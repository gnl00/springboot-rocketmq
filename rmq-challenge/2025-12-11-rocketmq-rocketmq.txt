  架构层面的 3 个新 Challenge 设计思路

  ---
  Challenge 12: 消息存储架构 - CommitLog + ConsumeQueue 设计

  核心架构思想：
  - RocketMQ 为什么采用 CommitLog（顺序写）+
  ConsumeQueue（索引）的分离设计？
  - 为什么不像 Kafka 那样按 Topic 分区存储？

  挑战场景：
  设计一个简化版的消息存储系统，对比两种架构：
  1. Buggy 版本：按 Topic 分别存储消息（模拟传统 MQ）
    - 多个 Topic 并发写入时，磁盘随机 IO 严重
    - Topic 数量增多时，文件句柄爆炸
    - 消息查询效率低
  2. Fixed 版本：实现 CommitLog + ConsumeQueue 架构
    - 所有消息顺序写入统一的 CommitLog
    - 每个 Topic 维护轻量级的 ConsumeQueue 索引
    - 支持按 offset、messageId、tag 快速查询

  学习目标：
  - 理解顺序写 vs 随机写的性能差异（可以用 JMH 测试）
  - 理解索引分离的设计思想
  - 学会在自己的系统中应用"数据与索引分离"的架构模式
  - 理解 PageCache、mmap、零拷贝等底层优化

  可应用场景：
  - 设计高性能日志系统
  - 设计时序数据库
  - 任何需要高吞吐写入的系统

  ---
  Challenge 13: 消费者负载均衡架构 - Rebalance 机制设计

  核心架构思想：
  - RocketMQ 的 Rebalance 为什么是客户端主动触发，而不是 Broker 推送？
  - 为什么要有 RebalanceStrategy（平均分配、一致性哈希、机房优先等）？
  - Rebalance 过程中如何保证消息不丢失、不重复？

  挑战场景：
  实现一个消费者动态扩缩容系统：
  1. Buggy 版本：简单的轮询分配
    - 消费者上下线时，消息分配不均
    - Rebalance 期间消息重复消费
    - 没有考虑消费者处理能力差异
  2. Fixed 版本：实现完整的 Rebalance 机制
    - 支持多种分配策略（AVG、一致性哈希、机房优先）
    - Rebalance 期间的消息暂停与恢复
    - 支持消费者权重配置
    - 实现优雅的 Rebalance 流程（暂停消费 → 释放队列 → 重新分配 → 恢复消费）

  学习目标：
  - 理解分布式系统中的负载均衡设计
  - 理解客户端协调 vs 服务端协调的权衡
  - 学会设计可扩展的策略模式
  - 理解一致性哈希在消息系统中的应用

  可应用场景：
  - 设计分布式任务调度系统
  - 设计微服务的动态负载均衡
  - 设计分布式爬虫系统

  ---
  Challenge 14: 高可用架构 - 主从同步与故障切换

  核心架构思想：
  - RocketMQ 的主从同步为什么有同步复制和异步复制两种模式？
  - Dledger 模式如何实现自动故障切换？
  - 如何在可用性、一致性、性能之间做权衡？

  挑战场景：
  实现一个高可用的消息存储系统：
  1. Buggy 版本：单机存储，无容灾
    - 主节点宕机后消息丢失
    - 无法实现异地多活
    - 没有数据备份机制
  2. Fixed 版本：实现主从同步架构
    - 支持同步复制（强一致性，低可用性）
    - 支持异步复制（高可用性，可能丢消息）
    - 实现 Raft 协议的简化版（Leader 选举、日志复制）
    - 支持故障自动切换
    - 实现读写分离（主写从读）

  学习目标：
  - 理解 CAP 理论在消息系统中的体现
  - 理解同步复制 vs 异步复制的权衡
  - 学习 Raft 协议的核心思想
  - 理解故障检测与自动切换机制

  可应用场景：
  - 设计分布式存储系统
  - 设计高可用的配置中心
  - 设计分布式缓存系统

  ---
  这 3 个 Challenge 的设计亮点

  1. 从"怎么用"到"为什么这样设计"

  - Level 1-11 教你如何正确使用 RocketMQ
  - Level 12-14 教你理解 RocketMQ 的架构设计哲学

  2. 可迁移的架构思想

  每个 Challenge 都提炼出可复用的架构模式：

  - 客户端协调的负载均衡（Challenge 13）
  - 主从复制与一致性权衡（Challenge 14）

  3. 动手实现简化版

  不是纸上谈兵，而是让学习者实现一个简化版的核心机制，真正理解设计的精妙之处
  。

  4. 性能对比与权衡分析

  每个 Challenge 都包含性能测试和权衡分析，让学习者理解架构决策背后的考量。

  // 文件大小显示 1GB，但实际占用很小（稀疏文件）
  System.out.println(channel.size()); // 1073741824

  方法 3: 使用 FileChannel.transferFrom()

  // 从 /dev/zero 读取数据填充文件（Linux）
  FileChannel zero = FileChannel.open(
      Paths.get("/dev/zero"),
      StandardOpenOption.READ
  );

  channel.transferFrom(zero, 0, 1024 * 1024 * 1024);

  🎯 Level 12 的真实 Bug

  现在 Buggy 版本的 Bug 描述更加准确了：

  Bug 1: 磁盘随机 IO 严重 ⭐⭐⭐⭐⭐

  - 多个 Topic 并发写入，磁盘磁头不断跳转
  - 性能从 500 MB/s 降到 50 MB/s

  Bug 2: 文件句柄爆炸 ⭐⭐⭐⭐

  - 每个 Topic 独立文件
  - 100 个 Topic = 100 个文件句柄

  Bug 3: 消息查询效率低 ⭐⭐⭐⭐⭐

  - 按 MessageId 查询需要遍历所有 Topic 文件
  - 查询延迟高达数秒

  Bug 4: 空间浪费与碎片化 ⭐⭐⭐

  - 文件系统块分配开销（每个文件至少 4KB）
  - 元数据开销（每个文件一个 inode）
  - 磁盘碎片化

  Bug 5: 无法支持多消费者组 ⭐⭐⭐

  - 所有消费者共享同一个文件
  - 无法独立维护消费进度
