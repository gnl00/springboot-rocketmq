  ✅ 你的解决方案评价

  核心问题理解 ✓

  你准确地发现了问题：
  - Producer 资源未被关闭 → 线程泄漏
  - 每个 Producer 会创建多个后台线程（心跳、网络通信等）
  - 不关闭就会导致线程数持续飙升（7000+！）

  解决方案正确 ✓

  你的 finally 块关闭 Producer 的做法是正确的：
  finally {
      if (producer != null) {
          try {
              producer.close();
              log.info("producer closed");
          } catch (IOException e) {
              log.error("producer close failed, e=", e);
          }
      }
  }

  优化点发现 ✓

  在 batchSendGood 中，你已经意识到应该在循环外创建 
  Producer，而不是每条消息都创建一个，这非常棒！

  💡 核心知识点

  1. RocketMQ 的投递语义

  - At Least Once：至少投递一次，可能重复
  - At Most Once：最多一次，可能丢失
  - Exactly Once：精确一次（需要自己实现幂等）

  2. 并发问题的根源

  - Check-Then-Act 模式：检查和操作不是原子的
  - 解决方案：使用原子操作（如 putIfAbsent）

  3. 异常处理策略

  - 业务异常（余额不足）：返回 SUCCESS，不重试
  - 系统异常（网络超时）：返回 FAILURE，触发重试

  4. 生产环境最佳实践

  - 持久化去重记录（数据库/Redis）
  - 定期清理过期数据
  - 多层防护（消息层 + 业务层）
  - 监控重复消息率
